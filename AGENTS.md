# Smart Campus Room Availability Checker

## Project
This is a small web application that helps students check if a campus room is available. It uses React, TypeScript and Vite. Rooms and bookings are fictional sample data.

## Project structure
- `src/lib/availability.ts` contains booking rules.
- `src/lib/time.ts` contains shared time conversion helpers.
- `src/components/RoomChecker.tsx` contains the user interface.
- `src/data.ts` contains sample rooms and bookings.
- `src/types.ts` contains shared types.
- `src/lib/availability.test.ts` contains Vitest tests for booking rules.
- `src/lib/filterRooms.ts` contains the pure room filtering logic (Assignment 04).
- `src/lib/filterRooms.test.ts` contains Vitest tests for room filtering.
- `src/lib/explain.ts` contains the optional mock "Explain availability" adapter and validation.
- `src/lib/explain.test.ts` contains Vitest tests for the explain feature.
- `src/components/RoomChecker.test.tsx` contains a Vitest UI test with React Testing Library.

## Acceptance criteria
- AC1: Reject invalid intervals and booking times in the past.
- AC2: Reject bookings longer than 120 minutes.
- AC3: Reject blocked rooms.
- AC4: Reject overlapping bookings, but allow touching endpoints.
- AC5: Return a clear decision without changing existing booking data.
- AC6: Keep clear feedback on desktop and mobile screens.

## Assignment 04 — room filtering
- New UI controls (attendees count and required equipment selection) may be added.
- Keep the existing visual style, responsive layout, and booking rules (AC1–AC6).
- Rooms carry an `equipment: string[]` field and a `RoomFilter` type drives filtering.
- `filterRooms(rooms, filters)` is a pure, non-mutating function.
- F1: rooms must have capacity >= requested attendees.
- F2: rooms must contain ALL selected required equipment items.
- F3: a blocked room is never reported as available (handled by checkAvailability).
- F4: show a clear message when no rooms match the filters.
- F5: changing the selected room refreshes the availability result appropriately.

## Optional mock Explain availability feature
- An optional "Explain availability" button may appear after a confirmed availability decision.
- The explanation is generated by a local mock adapter (`src/lib/explain.ts`), never a real API or external service.
- `checkAvailability` remains the only source of truth for availability status. The explain feature must not re-derive or override the decision.
- The adapter receives a structured summary (room label, times, reason code) — not raw booking objects or booking IDs.
- All inputs and outputs are validated: empty fields, malformed values, excessive lengths, unsupported reason codes, and status consistency (isAvailable vs reasonCode) are rejected without calling the adapter.
- Safe fallback handling is required for unavailable adapters, timeouts, adapter failures, and invalid model outputs.
- Explanations must be short, respectful, and use only confirmed information. Do not invent booking details or imply a booking can be created — this app does not create bookings.
- The explanation must be labeled as "Mock AI explanation" and displayed separately from the confirmed availability decision.
- If the student changes the room, time, attendees, or equipment, or starts a new availability check while an explanation is loading, the outdated response must not appear. A new check must also clear the old explanation and reset the loading state.
- Do not weaken or remove the existing explain tests.
